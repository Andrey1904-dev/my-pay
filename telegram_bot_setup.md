# CASE.PLACE SALARY — Telegram 2.0

Бот и PWA используют общие `settings` и `shifts` в Supabase. Бот работает в Edge Functions,
а GitHub Pages публикует только PWA. Публикация Pages не обновляет серверные функции.

## Ввод и ответы

Отправь `1250` или `1 250`: бот сохранит **итог**, заменив прежнее число за текущий день
`Asia/Yekaterinburg`. Допустимы целые значения 0–20 000 (существующий лимит приложения).
Отрицательные числа, дроби, выражения, `+500`, произвольный текст и ввод за прошлые дни
не сохраняются. Для истории, праздников, расходов и остальных настроек используется PWA.
Выходной по графику не запрещает фактическую смену.

Ответ — одно сообщение: статус, фактический заработок, шутка. Количество отдельной строкой
не выводится. Каждый ответ содержит `ReplyKeyboardRemove`. Новые клавиатуры не создаются.
Старые inline-кнопки ничего не меняют; при нажатии клавиатура старого сообщения очищается.

`_shared/telegram-jokes.ts` содержит 141 уникальную заранее написанную реакцию для
500–4000 с шагом 25 и две специальные. Выбор детерминированный, с округлением вниз.
Внешний AI API не используется.

Команды: `/start КОД`, `/help`, `/today`, `/month`, `/forecast`, `/calendar`, `/last`,
`/settings`, `/notify_on`, `/notify_off`, `/unlink`. Старые `/menu`, `/undo`, `/holiday`
сохранены как справочные команды. Изменение праздника и отмена старых добавлений
через Telegram больше не выполняются. Текстовые названия прежних разделов распознаются.

## Расчёт и надёжность

Формулы оплаты не менялись. Новая смена использует текущие индивидуальные настройки.
Обновление существующей сохраняет фиксированную ставку, премию, праздник и эффективный
сдельный тариф. `piece_rate` хранит тариф в том числе после замены количества на ноль.
Для старой смены без этого поля тариф выводится из сохранённой сделки; при совпадении
с действующим тарифом используется точное значение из настроек. Для старого нулевого
итога без снимка тарифа доступен только текущий тариф настроек.
Исторические строки бот не изменяет; существующая коррекция отображения legacy-тарифов сохранена.

`telegram_save_daily_total` — транзакционная service-only RPC. Она повторно проверяет
привязку чата, регистрирует `update_id`, блокирует строку, проверяет `updated_at` и
сохраняет смену вместе с отметкой обработки. Повторная доставка не может откатить новый итог.
Повтор того же числа не выполняет UPDATE смены. При ошибке транзакция откатывается.
При конфликте бот просит проверить итог и отправить новое сообщение.

PWA сохраняет исходную версию каждой смены и выполняет условный UPDATE/DELETE;
новая смена создаётся INSERT с защитой уникального ключа. При конфликте локальная очередь
остаётся на устройстве, а облачная смена не перезаписывается. Пользователь выбирает
«Оставить мою» или «Принять облачную». Проверка повторяется при новой гонке.
Пользователям ранее открытой старой PWA следует обновить страницу для этой защиты.

Напоминания и расписание cron сохранены. После внесения смены, включая нулевой итог,
напоминание о вводе не отправляется. Уведомления без кнопок. Уникальная запись
`telegram_reminder_deliveries(user_id,work_date,kind)` предотвращает повторы cron.
Выбрана доставка не более одного раза: при неоднозначной сетевой ошибке отправка
в этом слоте не повторяется, чтобы не прислать дубликат. Ошибка отражается в отчёте `failed`.
Ошибка чтения смен не трактуется как отсутствие смены.

## Обновление production

Проект: `dyixwxxpjmyycgigcbtx`. До этого обновления версии функций: бот **15**, напоминания **3**.
Предыдущий `main`: `ca63be4`. Секреты и webhook менять не нужно.

После проверок и CI, до публикации кода:

```bash
supabase db query --linked --project-ref dyixwxxpjmyycgigcbtx \
  --file supabase/updates/20261025_telegram_daily_total.sql
supabase functions deploy telegram-mypay telegram-reminders \
  --project-ref dyixwxxpjmyycgigcbtx --use-api --no-verify-jwt
supabase functions list --project-ref dyixwxxpjmyycgigcbtx
```

SQL-update добавляет nullable `shifts.piece_rate`, две служебные таблицы с RLS
и две service-only RPC, а также триггер версии смены. Не удаляет, не обновляет существующие смены и не меняет cron,
секреты, тарифы или настройки. Применяется транзакционно и повторно безопасен.
Не запускайте полный `SUPABASE_SCHEMA.sql`: он содержит отдельную миграцию старых тарифов.
Для новой установки после базовых SQL-файлов также выполните этот update.

Без JWT сохраняется существующий режим: бот проверяет `X-Telegram-Bot-Api-Secret-Token`,
напоминания — `Authorization: Bearer <service role key>`.
При вводе числа обработанная ошибка возвращает Telegram HTTP 200 и понятное сообщение
пользователю. После сетевого сбоя пользователь может повторить число; серверный журнал
защищает от повторного выполнения уже записанного update.

## Проверки

```bash
npm ci
npm run check
npm run build
npm audit
```

Тесты покрывают все 141 порог и каждый целый ввод внутри диапазонов, 143 уникальных текста,
границы, parser, создание/замену/повтор, реальные SQL-права и RPC в PGlite, премии,
праздник, историю, ноль, ошибки, гонки, повтор update, синхронизацию с PWA и cron.

После публикации: проверить ACTIVE/версии, GET бота (200), неправильный webhook-secret
(401), запуск cron без ключа (401), загрузку PWA. Безопасный smoke-тест исходников
обработчиков с production Supabase описан в `supabase/functions/telegram-smoke/index.ts`.
Он использует отдельный временный auth-аккаунт, перехватывает Telegram API и удаляет
тестовые данные; реальные чаты и смены не затрагиваются. Функция временная и после
проверки удаляется. Это не подтверждает визуальное отображение клавиатуры в Telegram
или реальную доставку сообщения/cron по внешней сети — эти проверки требуют тестового чата.
